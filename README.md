# RAG 기반 데이터시트 챗봇 (RAG ChatBot)

영문 하드웨어 데이터시트(PDF)를 분석해, 개발자가 질문했을 때 **한국어로 스펙과 출처 페이지를 함께 답변하는 RAG 기반 챗봇 프로젝트**입니다.  

---

## 1. 프로젝트 개요

- **진행 기간**: 2026.08 ~ 진행 중
- **프로젝트 형태**: 3인 팀 프로젝트
- **개발 배경 및 목적**
  - MCU, 센서, RTC 모듈 등의 영문 데이터시트는 분량이 길고 정보가 흩어져 있어 원하는 스펙을 빠르게 찾기 어렵습니다.
  - 일반적인 LLM만 사용할 경우 문서에 없는 정보를 생성하거나, 수치·단위를 잘못 답변할 가능성이 있습니다.
  - 이를 줄이기 위해 벡터 검색과 LLM을 결합한 RAG 구조를 바탕으로, **문서 근거 기반의 한국어 응답 시스템**을 구현하고자 시작했습니다.

## 2. 기술 스택

- **개발 언어**: Python
- **LLM**: Google Gemini API (`gemini-3.1-flash-lite`)
- **Validation / Schema**: Pydantic
- **Environment**: `python-dotenv`
- **Vector DB**: Chroma DB
- **문서 처리 / RAG 연동**: LangChain
- **Backend / UI 연동 대상**: FastAPI, Streamlit

## 4. 시스템 아키텍처 및 핵심 포인트

### 시스템 아키텍처

```text
[사용자 질문]
      ↓
[UI / API 계층]
      ↓
[벡터 검색 (Chroma DB)]
      ↓
[관련 청크 추출]
      ↓
[LLM 응답 엔진]
      ↓
[Pydantic 기반 구조화 응답]
      ↓
[답변 + 출처 페이지 반환]
```

### 핵심 포인트

- **문서 근거 기반 응답**
  - 검색된 데이터시트 청크를 바탕으로만 답변하도록 설계
  - 문서 외 정보 생성 가능성을 줄이는 방향으로 프롬프트 구성

- **구조화 출력**
  - 답변과 출처를 일정한 JSON 형태로 반환
  - 후속 UI 및 API 계층에서 안정적으로 처리할 수 있도록 구성

- **출처 페이지 검증**
  - 검색 청크에 존재하는 페이지 번호만 응답에 포함되도록 검증
  - 응답 신뢰성을 높이기 위한 후처리 로직 적용

- **검색 결과 부재 시 예외 처리**
  - 관련 청크가 없을 경우 불필요한 LLM 호출 없이 즉시 안내 문구 반환
  - 비용과 오답 가능성을 줄이는 방향으로 설계

## 7. 개발 과정에서 고려한 점

### 1) 구조화 출력의 필요성
자유 형식 문자열만으로는 UI나 API 계층에서 답변과 출처를 안정적으로 분리해 사용하기 어렵습니다.  
그래서 응답을 Pydantic 기반 JSON 구조로 고정해 후속 모듈이 일관되게 처리할 수 있도록 구성했습니다.

### 2) 문서 외 정보 생성 방지
하드웨어 데이터시트는 숫자와 단위의 정확성이 중요하기 때문에,  
문서에 없는 정보를 임의로 보완하거나 일반 상식으로 추정해 답변하는 방식은 지양해야 한다고 판단했습니다.  
이에 따라 문서 근거 기반 응답과 출처 페이지 포함을 핵심 원칙으로 두고 개발하고 있습니다.

### 3) 병렬 개발을 위한 입출력 규격 정리
RAG, AI, UI를 나누어 동시에 개발해야 했기 때문에,  
청크 입력 형식과 응답 JSON 구조를 먼저 정리해 각 파트가 독립적으로 개발할 수 있도록 맞췄습니다.

## 9. RAG 검색 파이프라인 (신승민)

데이터시트를 읽어 벡터로 저장하고, 질문과 관련된 부분을 찾아 AI 응답 계층에 넘기는 부분입니다.

### 9-1. 처리 흐름

```text
[PDF 업로드]
      ↓
[PDF 로드]            페이지 단위로 텍스트 추출
      ↓
[청크 분할]           검색 단위로 자르기 (토큰 기준)
      ↓
[임베딩]              텍스트 → 벡터 (OpenAI text-embedding-3-small)
      ↓
[Chroma 저장]         벡터 + 원문 + 페이지 번호
      ↓
[검색]                질문과 가까운 청크 추출
      ↓
[AI 응답 계층으로 전달]
```

### 9-2. 설계 시 고려한 점

- **페이지 번호 보존**
  - 로드 단계에서 부여한 페이지 번호가 청크와 벡터 저장까지 이어지도록 구성했습니다.
  - 출처 페이지는 뒤 단계에서 복원할 수 없는 정보라, 처음부터 끊기지 않게 가져가는 것을 기준으로 삼았습니다.

- **청크는 페이지 경계를 넘지 않도록 구성**
  - 분할기에 문서 전체가 아니라 페이지 단위로 입력을 주어, 하나의 청크가 두 페이지에 걸치지 않게 했습니다.
  - 답변에 인용할 출처 페이지를 하나로 확정하기 위한 선택입니다.

- **글자 수가 아닌 토큰 기준 분할**
  - 한국어와 영어는 같은 글자 수라도 토큰 수가 크게 달라, 글자 수 기준으로는 청크 크기가 일정하지 않습니다.
  - 임베딩 모델과 동일한 토크나이저(`cl100k_base`)를 사용해 크기를 셉니다.

- **벡터 데이터는 재생성 가능한 파생 데이터로 취급**
  - 원본 PDF만 있으면 벡터는 언제든 다시 만들 수 있도록 구성했습니다.
  - 청킹 설정을 바꿔가며 비교할 수 있도록 하기 위한 구조입니다.

### 9-3. AI 응답 계층과의 입출력 계약

검색 결과는 다음 형식으로 전달합니다.

```python
[
    {"text": "Operating voltage: 2.3V to 5.5V.", "page": 15},
    {"text": "Operating temperature range: ...",  "page": 13},
]
```

- 키 이름은 `text`, `page` 로 고정합니다.
- `page` 는 정수로 넘깁니다. 응답 계층이 출처 페이지를 검증할 때 청크의 페이지 집합과 비교하므로, 문자열로 넘기면 출처가 모두 제외됩니다.
- 검색 결과가 없을 경우 빈 리스트를 넘깁니다. 이때 응답 계층이 LLM을 호출하지 않고 안내 문구를 바로 반환합니다.

### 9-4. 실행 환경

의존성은 `pyproject.toml` 과 `uv.lock` 으로 관리합니다. 팀원 간 패키지 버전을 동일하게 맞추기 위해서입니다.

```bash
# uv 설치 (컴퓨터당 한 번)
# Windows PowerShell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# 저장소 폴더에서
uv sync
```

API 키는 두 개가 필요합니다. `.env.example` 을 복사해 `.env` 로 만든 뒤 채웁니다.

| 키 | 용도 |
| --- | --- |
| `OPENAI_API_KEY` | 문서와 질문을 벡터로 변환 (임베딩) |
| `GEMINI_API_KEY` | 답변 생성 |

실행은 프로젝트 가상환경으로 합니다.

```bash
uv run python rag_pipeline.py
```

패키지를 추가할 때는 `uv add <패키지>` 로 추가하고 `pyproject.toml` 과 `uv.lock` 을 함께 커밋합니다. 받는 쪽은 `uv sync` 로 반영합니다.

### 9-6. 확인된 제약

- **영문 문서에 한국어로 질문하는 경우**
  - 의미가 같아도 언어가 다르면 벡터 사이 거리가 더 멀게 측정됩니다.
  - 관련 있는 청크가 거리 기준에 걸려 제외되면 "해당 정보가 없습니다"로 응답이 나가기 때문에 원인이 드러나지 않습니다.
  - `VCC`, `I2C` 같은 영문 용어가 질문에 포함되면 완화되지만, 순수 한국어 질문에서는 그대로 나타납니다.
  - 거리 기준값은 실제 데이터시트로 측정한 뒤 조정할 예정입니다.

- **페이지를 넘어가는 표**
  - 청크가 페이지 경계를 넘지 않으므로, 표의 헤더 행과 값이 서로 다른 청크로 나뉘는 경우가 있습니다.
  - 여러 청크를 함께 검색해 응답 계층에서 종합하는 방식으로 완화하고 있으며, 표 구조 인식은 이후 개선 항목으로 두고 있습니다.
